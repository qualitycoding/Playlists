D-023 [R4] Target preflight before any write: all eight target IDs (Spotify master, Recently Added and six genres) pairwise distinct; each playlist owned by the authenticated user; Recently Added differs from every add-only ID; remote Recently Added holds at most 100 items, otherwise abort; target not full against the provider capacity limit (limits unverified, A-025). D-024 [R4] Circuit breaker for unsupervised runs after G-002b: abort if additions exceed new matched releases x K tracks, or if any add-only target's remote count has fallen since the last verified run; a manual-dispatch override input requires a logged reason. K is set from measured fixture data before G-002b (starting value 40 is unmeasured, A-026). The first run after migration is capped at a stated number of releases with resumable progress; the collection count (count only) is recorded in S-000a. [R5] After a manual-dispatch override with a logged reason the shrink baseline is reset to the current remote count; a shrink of at most M items (M unmeasured, A-026) is reported without aborting; the first-run cap counts the extra master-lookup calls of D-032.
D-025 [R4] Concurrency: workflow concurrency group "sync" with cancel-in-progress false. The state push fetches and rebases then retries; a push still rejected after provider writes fails the run red and the next run reconciles those rows from the unknown state. Each batch is deduplicated by provider URI before writing, so two releases sharing a master add each track once.
D-026 [R4] Exit-code contract: 0 all configured targets verified; 2 partial (some targets verified); 1 fatal. A configured target with missing or invalid credentials is fatal, never skipped. A dry-run exits 0 and its status is labelled dry-run, never success.
D-027 [R4][R5][owner 2026-11-07] Output privacy: the owner's Discogs collection and Spotify playlists are public (A-030), so artist, album and release IDs may appear in logs, step summaries, artefacts and gate evidence. Never allowed in any output: secrets, tokens, authorisation codes, cookies or headers, e-mail addresses and other account data, raw provider response bodies, and the contents of the encrypted state. Provider calls are logged through an allow-list of fields, not by dumping responses. Verified with a canary credential and a canary account identifier that must not appear in stdout, stderr, step summaries, artefacts, dist or gate evidence (T-052, T-045). The encrypted state artefact is ciphertext (it holds the rotated Spotify token, D-035); other artefacts may hold public-data evidence in plaintext. This relaxes the R4 rule that kept collection data out of outputs.
D-028 [R4][R5][R6] Gate integrity: every secret lives in a GitHub Environment and none at repository level; pull_request CI reads no secret. Environment gate-rehearsal has the owner as required reviewer and serves G-002a and the first G-002b run; Environment sync is limited to deployments from main, has no reviewer and holds the live secrets only after G-002b is recorded, so the schedule runs unattended. Changes to main need passing status checks (T-064, T-065) and zero approvals, because a one-account repository cannot give a PR approval (D-055). [R6] Gate approval is recorded as a GATE-<id>.md stating the approval channel (owner, in conversation, with date); while R-043 stands this is procedural and not enforced, and gate evidence proves process, not identity. Owner decision 2026-11-07: the implementing agent keeps running under the owner's admin credential for now, so an agent can still approve its own gate and bypass branch protection. This is an ACCEPTED RISK (R-043), not a closed finding; [R6] Agent-executable consequences of R-043: the agent can approve its own gate, change Environment reviewers and secrets, push to main and bypass branch protection, rewrite workflows, read or overwrite every Environment secret and disable the circuit breaker; every control that relies on an owner-only action is advisory until separation. Separating the agent identity (non-admin token or GitHub App, signed gate commits, prevent-self-review) is deferred and stays open. Availability of Environments, required reviewers and CODEOWNERS enforcement is unverified (A-022) and is checked in S-000a.

D-030 [R4] Workflow hardening: secrets reach a step only through env on the consuming step, never through ${{ secrets.* }} inside run or if; the YouTube auth file is written with printf '%s' from env or decoded from base64 [D-043: moot, no YouTube file exists]; the sync job holds provider secrets and read-only contents and uploads encrypted state; a separate commit job holds contents:write and no provider secrets; pip install uses --require-hashes, npm uses npm ci, actions are pinned to SHAs, runner is ubuntu-24.04; one Python minor version is chosen and recorded in S-000a (candidates 3.12 and 3.13, not yet verified on the runner); the legacy scheduled workflow is disabled in S-000a and re-enabled only at G-002b. [R5] Jobs: sync (provider secrets, read-only contents, uploads encrypted state), commit (contents:write, no provider secrets) and, in the separate pages.yml workflow (D-051), a deploy job that copies a prebuilt dashboard plus status.json from the state branch, with no Node at sync time. The upload and commit jobs run with if: always() after exit 0 or 2, and after exit 1 when a token rotated; the commit job checks the artefact's generation. [R6] pages.yml (renamed from deploy-pages.yml) is the only Pages publisher (D-044) and is started by a workflow_run trigger (D-051), not by needs. CI replacement (runner label, SHAs, hashed installs) happens in S-008; S-000a only records the pins and the Python version.
D-031 [R4] Status delivery and staleness: pages.yml deploys the status after each sync or rehearsal run through a workflow_run trigger (a push made with GITHUB_TOKEN does not trigger other workflows, D-051); the dashboard shows STALE when the last success is older than 8 days and labels dry-run status distinctly; the owner checks monthly that the schedule is still enabled (GitHub disables scheduled workflows in public repositories after 60 days without activity; whether bot commits count is unverified, A-024). [R5] Within a run the state commit precedes the status deploy. A separate scheduled check workflow (issues:write only, no secrets) opens an issue, which emails the owner, when the last success is more than 8 days old.
D-032 [R4][R5] Matching specification: normalise with NFKC and casefold; strip Discogs disambiguation suffixes "(n)" and trailing "*" name variations; escape quotes in provider queries; request K results (K>1, set in S-004 from the labelled fixture, unmeasured) and judge uniqueness over all K. Track rule: a provider album is not rejected for a differing track count alone; bonus or missing tracks are tolerated up to a count or ratio set from the fixture in S-004, and only a conflict between title sets rejects. Year rule: accept when the provider album date is at or after the Discogs master year, or within a tolerance set from the fixture; the master year costs one extra Discogs call per release, budgeted in D-024 and T-047, and a year check that cannot run leaves the release pending (not matched, retried next run) instead of being skipped; with no master release the release year is used (T-072). Various rule: Discogs "Various" matches only a provider album whose artist is "Various Artists" or "Various", by unique exact title; otherwise unmatched. Edition conflicts reject as in D-008. Precision and recall are reported on an owner-labelled fixture, run by the owner (T-067; it may be committed because the collection is public), while T-061 uses synthetic public data; the owner-agreed recall floor applies at G-002b only and G-006 governs rules beyond these. Each run reports the change in the unmatched count. Legacy cache rows are re-run through the matcher during migration; disagreements are reported and removal needs owner approval at G-004.
D-033 [R4] Recently Added semantics: take the 20 most recent matched releases, newest first; unmatched releases are skipped and reported; truncate to at most 100 tracks at whole-album boundaries; zero matched releases aborts without replacing; the encrypted snapshot is uploaded as an artefact of the sync job (ciphertext only) before the replace and the call order is asserted. [R5] An album of more than 100 tracks is skipped and reported; fewer than one matched album aborts without replacing.
D-034 [R4] Ledger identity and completeness: completion is recorded per (release, target); once read-back has confirmed an item it is never re-added automatically; reconciliation applies only to unknown rows; identity follows provider aliases (Spotify linked_from, YouTube setVideoId, moot under D-043); a playlist read is accepted only if complete against the provider total or snapshot; after N consecutive mismatches the target is quarantined and reported instead of re-adding (N unmeasured, A-026). Discogs ingestion deduplicates by instance_id, requires the unique count to equal pagination.items on both the first and last page, re-fetches page 1 at the end and fails closed if it changed, treats an empty non-final page as an error, and parses Retry-After as seconds or HTTP-date within a total-wait budget. [R5] Per target the ledger keeps the set of confirmed provider URIs (alias-aware) across all releases; a URI already confirmed in an add-only target is skipped for every later release, so a second pressing or reissue adds only tracks not already there. The never-re-add rule does not apply to Recently Added, which is replaced wholesale.
D-035 [R4][R5] State encryption and tokens: a pinned, audited AEAD (cryptography AESGCM) with a fresh random nonce per write, a key-ID header, and rotation by re-encryption; wrong or missing key aborts before any write with no plaintext fallback; a monotonic generation number in the associated data is checked against the counter in the committed status.json on the state branch, never read from the live site (D-044); an unreadable counter fails closed except on the first run, meaning state generation 0 with GATE-G-002b recorded; a status counter ahead of the state aborts the run and is cleared only by an owner re-anchor (manual dispatch input with a logged reason); within a run the state commit precedes the status deploy (D-031); rollbacks older than the last published status stay undetectable and this limit is accepted; the owner keeps an offline copy of the key; key loss is recovered by treating all ledger rows as unknown and running the G-004 duplicate report; the rotated Spotify refresh token is stored inside the encrypted state with an issued-at stamp, and after an owner reauthorisation the newer of the secret and the state token wins (a reauth marker forces the secret to win); Spotipy uses an in-memory cache handler (no .cache file); the Actions cache and artefact retention are never the source of truth. The setup scripts follow the same rules: in-memory cache, 127.0.0.1 loopback redirect, minimal scopes (playlist-read-private, playlist-modify-public, playlist-modify-private and no others), token written by `gh secret set --env sync` reading stdin, or to the encrypted state, and never printed or cached, and .gitignore gains .cache*; the reauthorisation is scheduled in S-002.
D-036 [R4] Test integrity and provider realism: every test file that exists when S-000b completes, not only TEST_PLAN.md, is hashed into FROZEN_MANIFEST.sha256 (the legacy tests/test_sync.py is hashed only after its rewrite) and CI runs sha256sum -c; S-000b first commits the NotImplementedError stubs, then writes the executable red tests and hashes them as its last action, before any source change; tests whose step has not yet run are listed in tests/xfail_ids.txt (outside the manifest, which hashes test bodies) and run as xfail(strict=True) by T-ID so main stays green, T-065 asserts the list only shrinks against the previous commit, and each step removes its own lines; amending a frozen test needs owner approval recorded here; existing tests that contradict D-008 (first-result match) or assert nothing about dry-run side effects are rewritten in S-000b; provider tests use recorded, sanitised read-only response fixtures and a fake provider that accepts duplicate items and enforces the 100-item limit; every live run starts with a read-only schema canary that fails closed, YouTube Music is probed with an authenticated call before any write [D-043: moot], and typed ProviderError is kept distinct from NoMatch with a breaker on unmatched-rate spikes. [R5] Recorded provider fixtures are captured read-only in S-002 and hashed at a second, batched freeze point at the end of S-002, with owner approval.

D-040 [R5] Genre routing: config.py holds an explicit map from each of the six genre lists (Electronic, Rock, Jazz, Hip-Hop, Funk / Soul, Classical) to its keywords and to its playlist-ID secret name, kept exactly as the owner's existing secrets are named (SPOTIFY_ELECTRONIC_PLAYLIST_ID, SPOTIFY_ROCK_PLAYLIST_ID, SPOTIFY_JAZZ_PLAYLIST_ID, SPOTIFY_HIP_HOP_PLAYLIST_ID, SPOTIFY_FUNK___SOUL_PLAYLIST_ID, SPOTIFY_CLASSICAL_PLAYLIST_ID); names are never derived from the genre label. D-044 [R6] Single Pages publisher: pages.yml (renamed from deploy-pages.yml) is the only workflow that deploys Pages and the sync workflow no longer deploys. status.json and the generation counter are committed on the state branch and read from there, never from the live site. D-046 [R6] Stage separation: ledger and confirmed-URI sets are keyed by provider playlist ID, so a retargeted ID starts empty. D-047 [R6] Token rotation: whether a Spotify refresh rotates the token is measured in S-002 (A-023). Local dry-runs use a separate Spotify authorisation and never touch the production token. An Actions dry-run or canary persists only a rotated token, through the commit job; this is the stated exception to success criterion 6.

D-054 [R7] State integrity and recovery: before every add to an add-only target the engine subtracts the URIs already present in the complete remote read; a missing state file after GATE-G-002b is fatal, not generation 0; the first-run cap applies to any target whose ledger is empty; quarantine has an exit (owner report command D-041, then a dispatch input with a logged reason); last-success and STALE are tracked per target; the capacity check fails only its own target (exit 2). D-058 [R8] Provider-neutral engine: the engine talks to a provider interface (search albums and tracks, resolve by barcode or ISRC, list playlist items completely, create playlist, add items, and for Recently Added replace if supported). Matching tries the Discogs barcode against the provider's album barcode first and falls back to the D-032 exact artist/title rule; track confirmation uses ISRC where the provider exposes it. A provider failing fails only its own targets (exit 2, D-054).
