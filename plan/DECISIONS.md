D-023 [R4] Target preflight before any write: all eight target IDs (Spotify master, Recently Added and six genres) pairwise distinct; each playlist owned by the authenticated user; Recently Added differs from every add-only ID; remote Recently Added holds at most 100 items, otherwise abort; target not full against the provider capacity limit (limits unverified, A-025). Targets must be private unless the owner accepts public exposure in writing at G-002a (the playlist-modify-public scope is dropped if unused). [R5] An unknown privacy state counts as non-private; dropping playlist-modify-public forces a re-consent, scheduled in S-002.
D-024 [R4] Circuit breaker for unsupervised runs after G-002b: abort if additions exceed new matched releases x K tracks, or if any add-only target's remote count has fallen since the last verified run; a manual-dispatch override input requires a logged reason. K is set from measured fixture data before G-002b (starting value 40 is unmeasured, A-026). The first run after migration is capped at a stated number of releases with resumable progress; the collection count (count only) is recorded in S-000. [R5] After a manual-dispatch override with a logged reason the shrink baseline is reset to the current remote count; a shrink of at most M items (M unmeasured, A-026) is reported without aborting; the first-run cap counts the extra master-lookup calls of D-032.
D-025 [R4] Concurrency: workflow concurrency group "sync" with cancel-in-progress false. The state push fetches and rebases then retries; a push still rejected after provider writes fails the run red and the next run reconciles those rows from the unknown state. Each batch is deduplicated by provider URI before writing, so two releases sharing a master add each track once.
D-026 [R4] Exit-code contract: 0 all configured targets verified; 2 partial (some targets verified); 1 fatal. A configured target with missing or invalid credentials is fatal, never skipped. A dry-run exits 0 and its status is labelled dry-run, never success.
D-027 [R4][R5] Collection privacy in outputs: logs, step summaries, artefacts and committed gate evidence carry only counts, run URLs and keyed hashes of identifiers (HMAC key held in the encrypted state); no artist, title, release row, account identifier or provider response body. Raw evidence (unmatched list, disagreement report, dry-run diff) lives only in the encrypted state or in an artefact encrypted with the state key, so every artefact is ciphertext (T-052). The commit cadence and ciphertext length reveal approximate collection size and run cadence; the owner accepts this metadata leak. Verified with a canary collection row (T-052, T-045).
D-028 [R4][R5] Gate integrity: every secret lives in a GitHub Environment and none at repository level; pull_request CI reads no secret. Environment gate-rehearsal has the owner as required reviewer and serves G-002a and the first G-002b run; Environment sync is limited to deployments from main, has no reviewer and holds the live secrets only after G-002b is recorded, so the schedule runs unattended. Changes to .github/workflows need a reviewed PR to main (CODEOWNERS and branch protection). A GATE-<id>.md counts only if added through a PR approved by the owner account. Owner decision 2026-11-07: the implementing agent keeps running under the owner's admin credential for now, so an agent can still approve its own gate and bypass branch protection. This is an ACCEPTED RISK (R-043), not a closed finding; separating the agent identity (non-admin token or GitHub App, signed gate commits, prevent-self-review) is deferred and stays open. Availability of Environments, required reviewers and CODEOWNERS enforcement is unverified (A-022) and is checked in S-000a.
D-029 [R4][R5] G-002 has two stages. G-002a: rehearsal on disposable private playlists and a preview, meaning the built dashboard served and smoke-tested in CI without deploying (Pages preview deployments are unverified, A-029); green CI at G-002a excludes T-040 and the production half of T-049. G-002b: first write to the real playlists, production Pages deploy and re-enabling of the schedule, after T-040 passes and the recall report exists.
D-030 [R4] Workflow hardening: secrets reach a step only through env on the consuming step, never through ${{ secrets.* }} inside run or if; the YouTube auth file is written with printf '%s' from env or decoded from base64; the sync job holds provider secrets and read-only contents and uploads encrypted state; a separate commit job holds contents:write and no provider secrets; pip install uses --require-hashes, npm uses npm ci, actions are pinned to SHAs, runner is ubuntu-24.04; one Python minor version is chosen and recorded in S-000 (candidates 3.12 and 3.13, not yet verified on the runner); the legacy scheduled workflow is disabled in S-000 and re-enabled only at G-002b. [R5] Jobs: sync (provider secrets, read-only contents, uploads encrypted state), commit (contents:write, no provider secrets) and deploy (copies a prebuilt dashboard plus status.json, no Node at sync time). The upload and commit jobs run with if: always() after exit 0 or 2, and after exit 1 when a token rotated; the commit job checks the artefact's generation. The deploy job and deploy-pages.yml share one Pages concurrency group. CI replacement (runner label, SHAs, hashed installs) happens in S-008; S-000a only records the pins and the Python version.
D-031 [R4] Status delivery and staleness: the sync workflow deploys the status itself (a push made with GITHUB_TOKEN does not trigger other workflows); the dashboard shows STALE when the last success is older than 8 days and labels dry-run status distinctly; the owner checks monthly that the schedule is still enabled (GitHub disables scheduled workflows in public repositories after 60 days without activity; whether bot commits count is unverified, A-024). [R5] Within a run the state commit precedes the status deploy. A separate scheduled check workflow (issues:write only, no secrets) opens an issue, which emails the owner, when the last success is more than 8 days old.
D-032 [R4][R5] Matching specification: normalise with NFKC and casefold; strip Discogs disambiguation suffixes "(n)" and trailing "*" name variations; escape quotes in provider queries; request K results (K>1, set in S-004 from the labelled fixture, unmeasured) and judge uniqueness over all K. Track rule: a provider album is not rejected for a differing track count alone; bonus or missing tracks are tolerated up to a count or ratio set from the fixture in S-004, and only a conflict between title sets rejects. Year rule: accept when the provider album date is at or after the Discogs master year, or within a tolerance set from the fixture; the master year costs one extra Discogs call per release, budgeted in D-024 and T-047, and the check is skipped rather than failed when the call is unavailable. Various rule: Discogs "Various" matches only a provider album whose artist is "Various Artists" or "Various", by unique exact title; otherwise unmatched. Edition conflicts reject as in D-008. Precision and recall are reported on a private labelled fixture, run by the owner and encrypted (T-067), while T-061 uses synthetic public data; the owner-agreed recall floor applies at G-002b only and G-006 governs rules beyond these. Each run reports the change in the unmatched count. Legacy cache rows are re-run through the matcher during migration; disagreements are reported and removal needs owner approval at G-004.
D-033 [R4] Recently Added semantics: take the 20 most recent matched releases, newest first; unmatched releases are skipped and reported; truncate to at most 100 tracks at whole-album boundaries; zero matched releases aborts without replacing; the snapshot is persisted (encrypted) before the replace and the call order is asserted. [R5] An album of more than 100 tracks is skipped and reported; fewer than one matched album aborts without replacing.
D-034 [R4] Ledger identity and completeness: completion is recorded per (release, target); once read-back has confirmed an item it is never re-added automatically; reconciliation applies only to unknown rows; identity follows provider aliases (Spotify linked_from, YouTube setVideoId); a playlist read is accepted only if complete against the provider total or snapshot; after N consecutive mismatches the target is quarantined and reported instead of re-adding (N unmeasured, A-026). Discogs ingestion deduplicates by instance_id, requires the unique count to equal pagination.items on both the first and last page, re-fetches page 1 at the end and fails closed if it changed, treats an empty non-final page as an error, and parses Retry-After as seconds or HTTP-date within a total-wait budget. [R5] Per target the ledger keeps the set of confirmed provider URIs (alias-aware) across all releases; a URI already confirmed in an add-only target is skipped for every later release, so a second pressing or reissue adds only tracks not already there. The never-re-add rule does not apply to Recently Added, which is replaced wholesale.
D-035 [R4][R5] State encryption and tokens: a pinned, audited AEAD (cryptography AESGCM) with a fresh random nonce per write, a key-ID header, and rotation by re-encryption; wrong or missing key aborts before any write with no plaintext fallback; a monotonic generation number in the associated data is checked against the counter in the previously deployed status.json, read over HTTPS; an unreachable source fails closed except on the first run after G-002b; a status counter ahead of the state aborts the run and is cleared only by an owner re-anchor (manual dispatch input with a logged reason); within a run the state commit precedes the status deploy (D-031); rollbacks older than the last published status stay undetectable and this limit is accepted; the owner keeps an offline copy of the key; key loss is recovered by treating all ledger rows as unknown and running the G-004 duplicate report; the rotated Spotify refresh token is stored inside the encrypted state with an issued-at stamp, and after an owner reauthorisation the newer of the secret and the state token wins (a reauth marker forces the secret to win); Spotipy uses an in-memory cache handler (no .cache file); the Actions cache and artefact retention are never the source of truth. The setup scripts follow the same rules: in-memory cache, 127.0.0.1 loopback redirect, minimal scopes without playlist-modify-public, token written to the secret or encrypted state and never printed or cached, and .gitignore gains .cache*; the reauthorisation is scheduled in S-002.
D-036 [R4] Test integrity and provider realism: every test file that exists when S-000 completes, not only TEST_PLAN.md, is hashed into FROZEN_MANIFEST.sha256 (the legacy tests/test_sync.py is hashed only after its rewrite) and CI runs sha256sum -c; the executable red tests are written and hashed as the last action of S-000, before any source change; amending a frozen test needs owner approval recorded here; existing tests that contradict D-008 (first-result match) or assert nothing about dry-run side effects are rewritten in S-000; provider tests use recorded, sanitised read-only response fixtures and a fake provider that accepts duplicate items and enforces the 100-item limit; every live run starts with a read-only schema canary that fails closed, YouTube Music is probed with an authenticated call before any write, and typed ProviderError is kept distinct from NoMatch with a breaker on unmatched-rate spikes. [R5] Recorded provider fixtures are captured read-only in S-002 and hashed at a second, batched freeze point at the end of S-002, with owner approval.
D-037 [R4] Provenance and diagnosis: S-006 first establishes where the legacy cache came from; rows absent from the live Discogs collection are dropped and never written; S-000 records the actual cause of the failed sync runs of 2026-11-07 (candidates: secrets in if, shell interpolation of the YouTube secret) before any rewrite.
D-038 [R4] Gate evidence additions: G-001 states the blast radius of the ytmusicapi credential (a whole Google-account session) and requires a dedicated or Brand account, or removal of YouTube Music; G-003 decides whether the planning-run copies of lessons/, knowledge/ and .checkpoints/ in the product repository are removed; G-005 lists the consequences of each option, including that a private repository loses free Pages (unverified) and the option of a separate private state repository.
D-039 [R4][R5] server.ts and the dev and start scripts that run it are deleted; Pages is static (D-002). T-066 asserts that no listen( call exists anywhere in the repository.
D-040 [R5] Genre routing: config.py holds an explicit map from each of the six genre lists (Electronic, Rock, Jazz, Hip-Hop, Funk / Soul, Classical) to its keywords and to its playlist-ID secret name, kept exactly as the owner's existing secrets are named (SPOTIFY_ELECTRONIC_PLAYLIST_ID, SPOTIFY_ROCK_PLAYLIST_ID, SPOTIFY_JAZZ_PLAYLIST_ID, SPOTIFY_HIP_HOP_PLAYLIST_ID, SPOTIFY_FUNK___SOUL_PLAYLIST_ID, SPOTIFY_CLASSICAL_PLAYLIST_ID); names are never derived from the genre label. Keywords match Discogs genre and style tags exactly after casefolding; a release may belong to several lists; ambiguous keywords (Contemporary, Fusion, Modal, Conscious, Disco, Trip Hop) are reviewed by the owner in S-004 and qualified by genre or removed. Configured means every one of the eight Spotify targets (master, Recently Added, six genres) has an ID (D-015), so a missing genre ID is fatal rather than skipped. T-069.
D-041 [R5] Owner visibility: a local, read-only report command decrypts the state with the owner's key and prints the unmatched list, the migration disagreement report and release IDs for overrides to the terminal only; it writes nothing to the repository, logs or artefacts (T-070). Unmatched releases are re-searched periodically (monthly, capped per run) in case catalogues or rules changed.
D-042 [R5] Live mode is refused unless GITHUB_ACTIONS is set, the ref is refs/heads/main and the expected Environment is present; local runs are dry-run only, so the local .env of A-003 is for dry-runs. GitHub keeps at most one pending run per concurrency group and a newer queued run cancels the older pending one (unverified, A-029), so a manual dispatch can displace the Sunday run; the STALE indicator and issue check of D-031 are the safeguard, and the owner avoids dispatching while a run is pending.
D-043 [G-001 outcome, owner decision 2026-11-07] YouTube Music is removed from release 1; the first release is Spotify-only (master, Recently Added, six genre lists). No YouTube adapter, credential, secret, auth script or workflow step is built. Tests and steps that concern YouTube Music keep their IDs but are marked deferred and are excluded from the release-1 pass criterion. Reintroduction needs a new G-001 with the D-038 evidence (blast radius, dedicated account or the official API quota limits). Basis: ytmusicapi is unofficial and needs a Google-account session as a secret; the official YouTube Data API charges 50 quota units per playlist insert against a 10,000 unit daily default and caps search calls (figures from Google's published quota table and secondary sources, to be re-checked on reintroduction).
