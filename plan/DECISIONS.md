D-026 [R4] Exit-code contract: 0 all configured targets verified; 2 partial (some targets verified); 1 fatal. A configured target with missing or invalid credentials is fatal, never skipped. A dry-run exits 0 and its status is labelled dry-run, never success. [R10] Amended by D-065..D-078.

D-031 [R4] Status delivery and staleness: pages.yml deploys the status after each sync or rehearsal run through a workflow_run trigger (a push made with GITHUB_TOKEN does not trigger other workflows, D-051); the dashboard shows STALE when the last success is older than 8 days and labels dry-run status distinctly; the owner checks monthly that the schedule is still enabled (GitHub disables scheduled workflows in public repositories after 60 days without activity; whether bot commits count is unverified, A-024). D-032 [R4][R5] Matching specification: normalise with NFKC and casefold; strip Discogs disambiguation suffixes "(n)" and trailing "*" name variations; escape quotes in provider queries; request K_search results (K_search>1, at most the provider's page limit, set in S-004 from the labelled fixture, unmeasured) and judge uniqueness over all K_search. Track rule: a provider album is not rejected for a differing track count alone; bonus or missing tracks are tolerated up to a count or ratio set from the fixture in S-004, and only a conflict between title sets rejects. Year rule: accept when the provider album date is at or after the Discogs master year, or within a tolerance set from the fixture; the master year costs one extra Discogs call per release, budgeted in D-024 and T-047, and a year check that cannot run leaves the release pending (not matched, retried next run) instead of being skipped; with no master release the release year is used (T-072). Various rule: Discogs "Various" matches only a provider album whose artist is "Various Artists" or "Various", by unique exact title; otherwise unmatched. Edition conflicts reject as in D-008. Precision and recall are reported on an owner-labelled fixture, run by the owner (T-067; it may be committed because the collection is public), while T-061 uses synthetic public data; the owner-agreed recall floor applies at G-002b only and G-006 governs rules beyond these. Each run reports the change in the unmatched count. Legacy cache rows are re-run through the matcher during migration; disagreements are reported and removal needs owner approval at G-004.
D-033 [R4] Recently Added semantics: take the 20 most recent matched releases, newest first; unmatched releases are skipped and reported; truncate to at most 100 tracks at whole-album boundaries; zero matched releases aborts without replacing; the encrypted snapshot is uploaded as an artefact of the sync job (ciphertext only) before the replace and the call order is asserted. [R5] An album of more than 100 tracks is skipped and reported; fewer than one matched album aborts without replacing.
D-034 [R4] Ledger identity and completeness: completion is recorded per (release, target); once read-back has confirmed an item it is never re-added automatically; reconciliation applies only to unknown rows; identity follows provider aliases (a provider alias where one exists: Spotify linked_from, removed in Development Mode and deferred with Spotify, D-050, D-057; YouTube playlist item IDs, D-063); a playlist read is accepted only if complete against the provider total or snapshot; after N consecutive mismatches the target is quarantined and reported instead of re-adding (N unmeasured, A-026). Discogs ingestion deduplicates by instance_id, requires the unique count to equal pagination.items on both the first and last page, re-fetches page 1 at the end and fails closed if it changed, treats an empty non-final page as an error, and parses Retry-After as seconds or HTTP-date within a total-wait budget. [R5] Per target the ledger keeps the set of confirmed provider URIs (alias-aware) across all releases; a URI already confirmed in an add-only target is skipped for every later release, so a second pressing or reissue adds only tracks not already there. The never-re-add rule does not apply to Recently Added, which is replaced wholesale.
D-035 [R4][R5] State encryption and tokens: a pinned, audited AEAD (cryptography AESGCM) with a fresh random nonce per write, a key-ID header, and rotation by re-encryption; wrong or missing key aborts before any write with no plaintext fallback; a monotonic generation number in the associated data is checked against the counter in the committed status.json on the state branch, never read from the live site (D-044); an unreadable counter fails closed except on the first run, meaning state generation 0 with GATE-G-002b recorded; a status counter ahead of the state aborts the run and is cleared only by an owner re-anchor (manual dispatch input with a logged reason); within a run the state commit precedes the status deploy (D-031); rollbacks older than the last published status stay undetectable and this limit is accepted; the owner keeps an offline copy of the key; key loss is recovered by treating all ledger rows as unknown and running the G-004 duplicate report; each provider's rotated refresh token is stored in its own encrypted file state/token.enc with an issued-at stamp (D-055), and after an owner reauthorisation the newer of the secret and the state token wins (a reauth marker forces the secret to win); Spotipy uses an in-memory cache handler (no .cache file); the Actions cache and artefact retention are never the source of truth. The setup scripts follow the same rules: in-memory cache, 127.0.0.1 loopback redirect, minimal scopes (playlist-read-private, playlist-modify-public, playlist-modify-private and no others), token written by `gh secret set --env sync` reading stdin, or to the encrypted state, and never printed or cached, and .gitignore gains .cache*; the reauthorisation is scheduled in S-002.
